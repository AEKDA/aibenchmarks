# Webhook Dispatcher — Техническое задание

Go-сервис надёжной доставки вебхуков потребителям. REST-приём событий,
гарантия доставки через transactional outbox, retry с экспоненциальным
бэкоффом и джиттером, подписанная HMAC-SHA256 отправка, перхостовый рейт-лимит.

## 1. Цели

- Принимать события по REST, связать их с подписчиками по типу события.
- Гарантировать доставку хотя бы с политикой retry (at-least-once) через outbox.
- Защитить подписчиков: подпись `X-Signature` и рейт-лимит на хост.
- Построить сервис на строгой гексагональной архитектуре: чистый домен,
  порты, адаптеры; юнит-тесты; без внешних интеграционных зависимостей в scope.

## 2. Сфера и вне сферы

**В сфере:** домен, REST-приём, worker-доставка, postgres-хранилище (SQL-миграции),
HTTP-сендер, рейт-лимитер, конфиг из ENV, graceful shutdown, юнит-тесты.

**Вне сферы:** docker-compose, интеграционные тесты против живой БД, реальные ретраи
HTTP-сендера (доставку ведёт worker), панель администрирования.

## 3. Требования

### 3.1 Доменная логика

- **State machine доставки**: `PENDING → SENDING → DELIVERED | RETRYING | DEAD_LETTER`.
- **Лимит попыток**: константа `MaxAttempts = 5` (включая первую).
- **Бэкофф**: `T = base × 2^attempt` с джиттером `±25%`; `base = 1s`.
- **Исход по HTTP-статусу**: `2xx → DELIVERED`; все прочие коды (включая
  `429/4xx/5xx`) → retry; исчерпание попыток → `DEAD_LETTER`.
- **Подпись**: `X-Signature: sha256=<hex(HMAC-SHA256(secret, body))>`.
- **Матчинг подписчиков**: по вхождению типа события в список подписки.

### 3.2 REST API (inbound)

- `POST /api/v1/subscriptions` — регистрация подписчика `{url, secret, events, max_rps}`.
- `POST /api/v1/events` — публикация события; обязательный заголовок
  `Idempotency-Key`; body `{type, payload}`.
- `GET /api/v1/deliveries/{id}` — статус доставки.

**Идпемпотентность:** повторная публикация с тем же `Idempotency-Key` не создаёт
нового события/доставок и возвращает маркер дубликата.

### 3.3 Постоянство и доставка

- **Outbox**: событие и его доставки сохраняются атомарно в одной транзакции.
- **Идпемпотентность** на уровне БД — уникальный индекс по `idem_key`, вставка
  с `ON CONFLICT DO NOTHING`.
- **Claim**: конкурентный забор задач `PENDING`/готовых `RETRYING`
  (`SELECT ... FOR UPDATE SKIP LOCKED`), перевод в `SENDING`.
- **Worker**: пул горутин, опрашивающий хранилище, доставляющий через HTTP-сендер
  с соблюдением рейт-лимита на хост.
- **RPS**: token-bucket на хост подписчика.

### 3.4 Подпись и рейт-лимит (outbound)

- Сендер шлёт `POST` с `Content-Type: application/json`, `User-Agent`, `X-Signature`.
- Лимитер блокирует отправку на хост, пока не появится слот.

## 4. Архитектурные ограничения

- `internal/application` импортирует **только** stdlib и `github.com/google/uuid`.
- Адаптеры не импортируют друг друга.
- Каждый метод порта и адаптера первым аргументом принимает `ctx`.
- Usecase/instruction = действие с методом `Invoke(...)`.
- Ошибки: пакет `errs` с типизированными `ErrNotFound/ErrConflict/ErrInvalid`,
  маппинг в HTTP-статусы `404/409/400` (+500).
- Моки только через minimock, рядом с интерфейсом.

## 5. Технологии

Go 1.27, `github.com/google/uuid`, `github.com/pkg/errors`,
`github.com/gojuno/minimock/v3`, PostgreSQL (pgx/v5), stdlib `net/http`.
