# Webhook Dispatcher - Epic Breakdown

## Overview

This document provides the complete epic and story breakdown for Webhook Dispatcher, decomposing the requirements from the PRD, UX Design if it exists, and Architecture requirements into implementable stories.

## Requirements Inventory

### Functional Requirements

Извлечено из `prd.md` §4. Идентификаторы сохранены как в PRD (FR-1 … FR-22) — downstream цитирует их напрямую.

**Управление подписками**
- **FR-1**: Подписчик регистрирует Подписку (URL, Секрет подписки, список типов Событий, `max_rps`); валидация URL, непустого списка типов, `max_rps` > 0, длины секрета ≥ 16.
- **FR-2**: Секрет подписки не возвращается ни в одном ответе API и не попадает в логи — включая предыдущий секрет в период Плавного перехода.
- **FR-3**: Ротация Секрета подписки через `POST /api/v1/subscriptions/{id}/secret/rotate` с Плавным переходом 24 ч; повторная ротация внутри активного перехода — `409`.

**Публикация событий и идемпотентность**
- **FR-4**: Публикация События через `POST /api/v1/events` возвращает `202` с идентификатором События и списком идентификаторов Попыток доставки до какой-либо сетевой отправки.
- **FR-5**: Заголовок `Idempotency-Key` обязателен; без него — `400`, Событие не создаётся.
- **FR-6**: Повторная публикация с тем же Ключом идемпотентности возвращает исходный результат и не создаёт новых Попыток доставки; конкурентные запросы дают ровно одно Событие; то же тело — исходный ответ, другое тело — `409`.
- **FR-7**: Событие и все порождённые Попытки доставки сохраняются атомарно (Transactional Outbox); Попытки создаются в статусе `PENDING`.
- **FR-8**: Попытка доставки создаётся для каждой Подписки, чей список типов Событий содержит тип опубликованного События.

**Доставка, машина состояний и повторы**
- **FR-9**: Машина состояний доставки допускает только `PENDING→SENDING`, `SENDING→DELIVERED`, `SENDING→RETRYING`, `RETRYING→SENDING`, `SENDING→DEAD_LETTER`; `DELIVERED` и `DEAD_LETTER` терминальны; недопустимый переход — типизированная доменная ошибка.
- **FR-10**: Воркер получает пачку Попыток доставки, готовых к отправке (`PENDING` и `RETRYING` с наступившим моментом); одна Попытка не выдаётся двум Воркерам.
- **FR-11**: Аренда Попытки доставки и восстановление брошенных: Реапер возвращает `SENDING` с истёкшей Арендой в `RETRYING`; Таймаут аренды строго больше таймаута отправки.
- **FR-12**: Исходящее соединение блокируется по фактическому IP перед установкой: loopback, приватные диапазоны, link-local, `169.254.169.254`; блокировка — неуспех попытки с видимой причиной.
- **FR-13**: Отправка вебхука — HTTP POST, `Content-Type: application/json`, таймаут 5 с, кастомный `User-Agent`, отменяемый контекст.
- **FR-14**: Классификация результата: 2xx — `DELIVERED`; 4xx (кроме 429), 5xx, таймаут, сетевая ошибка — `RETRYING` до лимита, затем `DEAD_LETTER`; 429 расходует попытку и планируется по FR-18.
- **FR-15**: Подпись полезной нагрузки `X-Signature: sha256=<hex_digest>` — HMAC-SHA256 от точных байтов тела на Секрете подписки, неизменна между повторами.
- **FR-16**: Двойная подпись в период Плавного перехода: `X-Signature: sha256=<new>,sha256=<prev>`, новая первой; после истечения — одна.
- **FR-17**: Задержка повтора `T = base × 2^attempt ± jitter`, `base = 1s`, неотрицательна, не выше потолка, монотонна по Номеру попытки.
- **FR-18**: Повтор по указанию Подписчика: `Retry-After` при 429 в обеих формах (секунды и HTTP-date), усечение по потолку; некорректный или отсутствующий — увеличенный бэкофф.
- **FR-19**: Предел 5 попыток, затем `DEAD_LETTER`; Мёртвое письмо остаётся видимым через Delivery Status API.
- **FR-20**: Двухуровневое ограничение скорости: токен нужен и в бакете Подписки (`max_rps`), и в бакете Целевого хоста; отказ откладывает отправку без расхода Номера попытки.

**Наблюдаемость и жизненный цикл**
- **FR-21**: `GET /api/v1/deliveries/{id}` возвращает Статус доставки, Номер попытки, момент следующей попытки, код и время последнего ответа; неизвестный идентификатор — `404`, некорректный формат — `400`.
- **FR-22**: Graceful shutdown: прекращение приёма новых запросов, дообработка начатых, остановка Воркеров и Реапера, нулевой код возврата в пределах таймаута.

### NonFunctional Requirements

Извлечено из `prd.md` §5 и §9.

- **NFR-1** (Надёжность): гарантия доставки at-least-once; Подписчик обязан быть идемпотентен на своей стороне.
- **NFR-2** (Надёжность): ни одно принятое Событие не теряется при перезапуске процесса — состояние доставки живёт в хранилище, не в памяти.
- **NFR-3** (Надёжность): порядок доставки Событий не гарантируется.
- **NFR-4** (Конкурентность): отсутствие гонок данных — сборка и тесты проходят с флагом `-race`.
- **NFR-5** (Конкурентность): отсутствие утечек горутин — все запущенные горутины завершаются при завершении процесса.
- **NFR-6** (Производительность): Publish API отвечает быстро, не выполняя сетевую отправку синхронно; конкурентность доставки ограничена размером Пула воркеров и `max_rps`.
- **NFR-7** (Безопасность): Секрет подписки не появляется в ответах API, логах и трассировках.
- **NFR-8** (Безопасность): вычисление и сравнение подписи устойчивы к атакам по времени.
- **NFR-9** (Безопасность): ни один исходящий запрос не достигает внутренней сети или сервиса метаданных облака.
- **NFR-10** (Наблюдаемость): каждый Переход состояния логируется структурированно с полями `delivery_id`, `event_id`, `subscription_id`, `attempt`, `status`, кодом ответа.
- **NFR-11** (Наблюдаемость): полезная нагрузка События не логируется целиком.
- **NFR-12** (Сопровождаемость): строгая гексагональная архитектура — домен без внешних зависимостей, адаптеры не зависят друг от друга.
- **NFR-13** (Сопровождаемость): `ctx context.Context` первым аргументом во всех методах портов и адаптеров.
- **NFR-14** (Сопровождаемость): типизированные доменные ошибки, обёртка через `%w`, маппинг в HTTP-статусы только в HTTP-адаптере.
- **NFR-15** (Тестируемость): чистый домен покрыт unit-тестами (машина состояний, бэкофф, подпись) без БД, сети и реального времени.
- **NFR-16** (Эксплуатация): выборка Попыток доставки остаётся корректной при нескольких экземплярах сервиса.

### Additional Requirements

Извлечено из `ARCHITECTURE-SPINE.md`. Стартового шаблона (starter template) архитектура не предписывает — проект собирается с нуля на stdlib плюс четыре зависимости, поэтому первая история Эпика 1 — это ручной скелет, а не разворачивание генератора.

**Стек (проверен по вебу на дату архитектуры):** Go 1.27, PostgreSQL 18.6, `github.com/jackc/pgx/v5` v5.10.0, `github.com/google/uuid` v1.6.0, `golang.org/x/time/rate` v0.15.0, `golang.org/x/sync/errgroup`. Маршрутизация — `http.ServeMux`, логирование — `log/slog`. Веб-фреймворк и ORM не вводятся.

**Инфраструктура и развёртывание**
- Один бинарь, N реплик; HTTP-сервер и Пул воркеров в одном процессе.
- Координация реплик исключительно через `FOR UPDATE SKIP LOCKED` — ни выборов лидера, ни распределённых блокировок (AD-9).
- Миграции — нумерованные SQL-файлы в `migrations/`, только вперёд, применяются отдельной задачей до выката реплик.
- Окружения различаются только конфигурацией; артефакт один.

**Архитектурные инварианты, влияющие на истории**
- AD-1: `application/**` импортирует только stdlib и `uuid`; адаптеры не импортируют друг друга. Проверяется тестом на импорты в CI.
- AD-2: интерфейсы объявлены в `application/ports`, названы по роли, без типов адаптерных библиотек в сигнатурах.
- AD-3: usecase — глагол, единственный метод `Invoke(ctx, in) (out, error)`.
- AD-5: sentinel-ошибки `ErrNotFound`, `ErrConflict`, `ErrValidation`, `ErrInvalidTransition`, `ErrBlockedTarget`; трансляция ошибок технологии в доменные — обязанность driven-адаптера.
- AD-6: транзакции только через `TxManager.WithinTx(ctx, fn)`; транзакция едет в `ctx`, usecase не видит `pgx.Tx`; вложенный вызов переиспользует.
- AD-7: идемпотентность на уникальном индексе `events.idempotency_key`, конфликт распознаётся по коду ошибки БД; хеш тела — SHA-256 hex.
- AD-8: переходы статуса только методами `entity.DeliveryAttempt`; репозиторий сохраняет сущность целиком. Единственное исключение — атомарная выборка с арендой.
- AD-9: выборка задач — один `UPDATE ... FROM (SELECT ... FOR UPDATE SKIP LOCKED)`; отдельного шага «взять аренду» нет.
- AD-10: `Clock` и `RandSource` — порты; домен не вызывает `time.Now()` и не создаёт источники случайности.
- AD-11: полезная нагрузка хранится как `bytea`, не `jsonb`, и не проходит цикл разбор-сборка — иначе HMAC повтора не совпадёт с исходным.
- AD-12: HMAC считает instruction в домене; `WebhookSender` получает готовые заголовки и не знает про секрет.
- AD-13: `WebhookSender.Send` возвращает факты (код, `Retry-After`, признак таймаута, признак блокировки), решения принимает `ClassifyResponse`.
- AD-14: `RateLimiter.Allow` без ожидания; отказ снимает аренду и возвращает задачу через `Requeue(at)`; хост извлекается из `target_url` в usecase'е.
- AD-15: SSRF-guard — кастомный `DialContext`, проверка по фактическому IP; редиректы запрещены (`CheckRedirect` возвращает ошибку).
- AD-16: окружение читает только `cmd/dispatcher`, префикс `WHD_`; при старте валидируется инвариант «таймаут аренды > таймаута отправки».
- AD-17: HTTP-сервер, Пул воркеров и Реапер реализуют `Run(ctx) error`; корневой контекст из `signal.NotifyContext`, запуск через `errgroup`.
- AD-18: `entity.Secret` имеет `String()` и `MarshalJSON()`, возвращающие `[REDACTED]`; HTTP-адаптер использует отдельные DTO.
- AD-19: идентификаторы — UUIDv7, генерируются в домене; БД не назначает `DEFAULT` на первичном ключе.
- AD-20: единая форма ошибки API `{"error": {"code": "...", "message": "..."}}`.
- AD-21: `log/slog`, логирование только в адаптерах и composition root; домен не логирует.
- AD-22: Номер попытки инкрементируется ровно один раз — в момент фактической выдачи HTTP-запроса; SQL-выборка, Реапер и путь отказа лимитера его не трогают.
- AD-23: `next_attempt_at` назначают только методы сущности; потолок задержки применяется в `CalculateBackoff` и распространяется на `Retry-After`.

**Индексы, несущие инвариант:** уникальный на `events.idempotency_key`; частичный по `delivery_attempt (status, next_attempt_at)`.

**Известное ограничение v1:** Ограничитель скорости локален для реплики — при N репликах фактический потолок Целевого хоста равен N × лимит (в `Deferred` архитектуры).

### UX Design Requirements

Не применимо. У сервиса нет пользовательского интерфейса: все три точки входа — REST API для машин, потребители — внутренние сервисы и интеграционный код подписчиков. UX-документ в `{planning_artifacts}` отсутствует и не требуется.

Эквивалент UX-контракта для этого продукта — форма API: единая структура ошибки (AD-20), стабильные коды ошибок и заголовок `X-Signature`, который реализует код на стороне подписчика. Эти требования покрыты FR-1, FR-15, FR-16, FR-21 и AD-20, а не отдельным разделом.

## Epic List

### Эпик 1: Приём событий без потерь

Продюсер регистрирует подписчиков и публикует События одним вызовом, получая `202` до какой-либо сетевой отправки. Повторный вызов с тем же `Idempotency-Key` не создаёт дублей. Событие и его Попытки доставки сохраняются атомарно — падение процесса после `202` ничего не теряет.

**FRs covered:** FR-1, FR-2, FR-4, FR-5, FR-6, FR-7, FR-8, FR-9, FR-22
**Standalone:** да. Работающий сервис приёма; доставки ещё нет, но контракт продюсера уже выполняется и данные в безопасности.

### Эпик 2: Доставка с повторами

Подписчик получает подписанный вебхук. Недоступный подписчик не теряет Событие: повторы с экспоненциальной задержкой и джиттером, Аренда против зависших отправок, `DEAD_LETTER` по исчерпании лимита.

**FRs covered:** FR-10, FR-11, FR-13, FR-14, FR-15, FR-17, FR-18, FR-19
**Standalone:** да, опирается на Эпик 1. После этого эпика сервис делает то, ради чего существует.

### Эпик 3: Безопасное включение в проде

Сервис можно направить на внешних подписчиков: исходящие соединения не уходят во внутреннюю сеть, Секрет подписки ротируется без окна отказов, скорость ограничена на двух уровнях.

**FRs covered:** FR-3, FR-12, FR-16, FR-20
**Standalone:** да, опирается на Эпик 2.

### Эпик 4: Ответ на «мы не получили событие»

Дежурный инженер за один запрос видит судьбу Попытки доставки: статус, Номер попытки, момент следующей попытки, код и время последнего ответа. Каждый Переход состояния находится в логах по идентификатору.

**FRs covered:** FR-21 (плюс NFR-10, NFR-11)
**Standalone:** да, подключается после Эпика 2.

## Epic 1: Приём событий без потерь

Продюсер регистрирует подписчиков и публикует События одним вызовом, получая `202` до какой-либо сетевой отправки. Повторный вызов с тем же `Idempotency-Key` не создаёт дублей. Событие и его Попытки доставки сохраняются атомарно.

### Story 1.1: Скелет сервиса с жёсткими границами слоёв

As a разработчик команды,
I want проект со сборкой, конфигурацией, жизненным циклом и автоматической проверкой архитектурных границ,
So that каждая последующая история добавляет функциональность, а не переизобретает каркас, и слои не расползаются незаметно.

**Acceptance Criteria:**

**Given** пустой репозиторий
**When** выполняется `go build ./...`
**Then** собирается бинарь `cmd/dispatcher`

**Given** DNS-имя, резолвящееся в приватный диапазон
**When** выполняется отправка
**Then** проверка срабатывает по фактическому разрешённому IP непосредственно перед соединением, а не по строке URL

**Given** заблокированная попытка соединения
**When** формируется результат
**Then** он несёт признак блокировки, Попытка доставки планируется в `RETRYING`, а при исчерпании лимита переходит в `DEAD_LETTER`
**And** причина блокировки сохраняется как результат последней попытки

**Given** табличный набор адресов, разрешённых и запрещённых
**When** выполняются unit-тесты правила проверки
**Then** все случаи классифицированы верно

**Given** очерёдность фильтров
**When** цель заблокирована
**Then** проверка выполняется после Ограничителя скорости — блокировка не расходует токены

### Story 3.2: Ротация Секрета подписки

As an интеграционный инженер подписчика,
I want заменить утёкший секрет без остановки доставок,
So that ротация не требовала окна простоя и согласования по времени.

**Acceptance Criteria:**

**Given** существующая Подписка
**When** выполняется `POST /api/v1/subscriptions/{id}/secret/rotate`
**Then** возвращается `200 OK`, новый Секрет подписки становится основным, предыдущий сохраняется, момент окончания Плавного перехода установлен на 24 часа вперёд

**Given** ответ на ротацию
**When** он читается
**Then** он не содержит ни нового, ни предыдущего Секрета подписки

**Given** активный Плавный переход
**When** выполняется повторная ротация
**Then** возвращается `409 Conflict`

**Given** неизвестный идентификатор Подписки
**When** выполняется ротация
**Then** возвращается `404 Not Found`

**Given** истёкший момент Плавного перехода
**When** читается Подписка
**Then** предыдущий Секрет подписки считается недействующим независимо от того, удалён он физически или нет

**Given** Попытки доставки в статусе `SENDING` в момент ротации
**When** они завершаются
**Then** ротация на них не влияет

### Story 3.3: Двойная подпись в период Плавного перехода

As an интеграционный инженер подписчика,
I want чтобы в течение суток после ротации запросы несли обе подписи,
So that я мог выкатить новый секрет в удобный момент, а не синхронно с ротацией.

**Acceptance Criteria:**

**Given** Подписка вне Плавного перехода
**When** отправляется вебхук
**Then** заголовок `X-Signature` содержит ровно одну подпись

**Given** Подписка с действующим Плавным переходом
**When** отправляется вебхук
**Then** заголовок содержит две подписи через запятую в формате `sha256=<new>,sha256=<prev>`, новая первой

**Given** запрос с двумя подписями
**When** подписчик проверяет любую одну из них своим секретом
**Then** проверка проходит

**Given** Подписка, чей Плавный переход истёк
**When** отправляется вебхук
**Then** вторая подпись отсутствует в заголовке

**Given** формирование значения заголовка
**When** проверяется код
**Then** оно собирается одним instruction'ом в домене, а отправитель его только передаёт

### Story 3.4: Двухуровневое ограничение скорости

As an интеграционный инженер подписчика,
I want чтобы сервис уважал заявленную мной скорость и не заваливал общий хост,
So that доставка вебхуков не превращалась в DDoS моей инфраструктуры.

**Acceptance Criteria:**

**Given** Подписка с `max_rps = 10`
**When** воркеры отправляют ей вебхуки под нагрузкой
**Then** частота отправок не превышает 10 в секунду в пределах измеримого окна

**Given** несколько Подписок, разделяющих один Целевой хост, сумма `max_rps` которых превышает лимит хоста
**When** воркеры отправляют вебхуки
**Then** совокупная частота отправок на этот Целевой хост не превышает лимит хоста

**Given** запрос токена
**When** он выполняется
**Then** проверяются оба уровня в одном вызове, и при отказе второго уровня токен первого возвращается обратно

**Given** отказ Ограничителя скорости
**When** обрабатывается Попытка доставки
**Then** Аренда снимается, Попытка возвращается в `RETRYING` с коротким смещением через метод сущности
**And** Номер попытки не увеличивается и результат последнего ответа не изменяется

**Given** медленный целевой хост
**When** воркер получает отказ лимитера
**Then** воркер не блокируется в ожидании — вызов неблокирующий, воркер берёт следующую задачу

**Given** несколько реплик сервиса
**When** измеряется фактическая частота на Целевой хост
**Then** документация признаёт, что лимит локален для реплики и совокупный потолок равен N × лимит — обещания глобального потолка в тестах нет

## Epic 4: Ответ на «мы не получили событие»

Дежурный инженер за один запрос видит судьбу Попытки доставки. Каждый Переход состояния находится в логах по идентификатору.

### Story 4.1: Статус доставки по идентификатору

As a дежурный инженер,
I want одним запросом узнать судьбу конкретной доставки,
So that разговор с партнёром переходил от «у вас баг» к конкретной причине без чтения логов.

**Acceptance Criteria:**

**Given** существующая Попытка доставки
**When** выполняется `GET /api/v1/deliveries/{id}`
**Then** возвращается `200 OK` со Статусом доставки, Номером попытки, моментом следующей попытки, кодом последнего ответа и моментом последней попытки

**Given** Попытка доставки в статусе `DEAD_LETTER`
**When** запрашивается её статус
**Then** она видна вместе с числом сделанных попыток и результатом последнего ответа

**Given** Попытка доставки, заблокированная защитой исходящих соединений
**When** запрашивается её статус
**Then** причина блокировки видна как результат последней попытки

**Given** неизвестный идентификатор
**When** выполняется запрос
**Then** возвращается `404 Not Found` в единой форме ошибки

**Given** идентификатор некорректного формата
**When** выполняется запрос
**Then** возвращается `400 Bad Request` в единой форме ошибки

**Given** любой ответ этого эндпоинта
**When** он читается
**Then** он не содержит Секрета подписки и не содержит внутренних деталей — ни SQL, ни имён таблиц

### Story 4.2: Структурированные логи переходов состояния

As a дежурный инженер,
I want находить всю историю доставки по одному идентификатору,
So that расследование инцидента не требовало сопоставления разрозненных записей.

**Acceptance Criteria:**

**Given** доставка, прошедшая путь от публикации до терминального статуса
**When** логи фильтруются по `delivery_id`
**Then** видна вся последовательность Переходов состояния

**Given** любая запись лога о доставке
**When** она читается
**Then** она структурирована и несёт поля `delivery_id`, `event_id`, `subscription_id`, `attempt`, `status`

**Given** запись лога об отправке
**When** она читается
**Then** дополнительно присутствуют код ответа и длительность запроса

**Given** любая запись лога
**When** она проверяется
**Then** она не содержит полезной нагрузки События целиком и не содержит Секрета подписки

**Given** пакеты слоя `internal/application`
**When** они проверяются
**Then** в них нет вызовов логирования — логируют только адаптеры и composition root
