- (capability) CAP-1 Регистрация и ротация подписок: подписчик регистрирует эндпоинт (URL, секрет, типы событий, max_rps) и безопасно ротирует утёкший секрет без перерыва доставки, 24ч двойная подпись; успех: POST /api/v1/subscriptions→201+id без секрета, ротация→200, повторная-ротация-в-переходе→409.
- (capability) CAP-2 Публикация с идемпотентностью и outbox: продюсер публикует Событие одним вызовом, повтор с тем же Idempotency-Key не создаёт дублей; успех: 202+id, без-ключа→400, тот-ключ-иное-тело→409, атомарная запись Event+Deliveries, маршрутизация по типу события.
- (capability) CAP-3 Машина состояний доставки: Попытка доставки проходит разрешённые переходы PENDING→SENDING→DELIVERED/RETRYING→DEAD_LETTER без застревания, аренда и реапер; успех: недопустимый переход→доменная ошибка, ни одна запись не виснет в SENDING дольше таймаута аренды+периода реапера.
- (capability) CAP-4 Доставка с HMAC-подписью и повторами: HTTP POST c X-Signature, повтор по экспоненциальному бэкоффу с джиттером и Retry-After, лимит 5 попыток затем DEAD_LETTER; успех: X-Signature: sha256=..., 429 уважает Retry-After, после 5 неуспехов DEAD_LETTER, первый-бэк/Retry-After из FR-17/FR-18.
- (capability) CAP-5 Защита исходящих соединений от SSRF: система не соединяется с внутренней сетью и метаданными облака; успех: блокировка по фактическому IP перед соединением (не по строке URL), табличный тест, loopback/private/link-local/169.254.169.254 заблокированы, редиректы запрещены.
- (capability) CAP-6 Двухуровневое ограничение скорости: не превышаются ни max_rps подписки, ни лимит целевого хоста; успех: оба лимита соблюдаются в окне, отказ лимитера не расходует номер попытки и не пишет результат.
- (capability) CAP-7 Наблюдаемость доставки: дежурный за один запрос узнаёт статус Попытки доставки; успех: GET /api/v1/deliveries/{id}→200 со статусом, номером попытки, моментом следующей, кодом и временем последнего ответа; неизвестный id→404, неверный формат→400.
- (capability) CAP-8 Жизненный цикл процесса: сервис корректно завершается по сигналу, не бросая начатую работу; успех: прекращение приёма новых запросов, дообработка начатых, воркеры/реапер останавливаются, exit 0 в пределах таймаута, брошенные SENDING подхватывает реапер.
- (constraint) Доставка at-least-once: подписчик готов к повторам, порядок событий не гарантируется; состояние доставки живёт в хранилище, не в памяти.
- (constraint) Строгая гексагональная архитектура: домен импортирует только stdlib и uuid; адаптеры не зависят друг от друга; единственный импортер адаптеров и единственный читатель окружения — cmd/dispatcher; границы проверяются тестом импортов.
- (constraint) Атомарность Событие+Попытки доставки (Transactional Outbox) в одной транзакции; идемпотентность обеспечивает уникальный индекс по ключу, а не check-then-insert.
- (constraint) Полезная нагрузка — неизменяемые []byte (bytea в БД), подпись HMAC от тех же байтов, без цикла разбор-сборка; UUIDv7 генерируются в домене, не в БД.
- (constraint) ctx context.Context первым аргументом всех методов IO; хранение ctx в полях запрещено; ошибки типизированные в домене, маппинг в HTTP-статус только в driver/http; секрет не появляется в ответах/логах ([REDACTED]); payload и секреты не логируются целиком.
- (constraint) SSRF-guard по фактическому IP перед соединением; таймаут аренды строго больше таймаута отправки (инвариант проверяется при старте).
- (non-goal) Не брокер сообщений общего назначения: нет подписки на чтение, consumer groups, воспроизведения истории.
- (non-goal) Нет exactly-once, нет гарантии порядка, нет UI, нет трансформации payload под подписчика.
- (non-goal) Нет аутентификации продюсеров и мультитенантности в v1 (защита периметром); нет транспортов кроме HTTP POST.
- (non-goal) v2: изменение/удаление подписки (кроме ротации секрета), ручной рестарт dead letters, листинг доставок с фильтрами, верификация владения эндпоинтом, circuit breaker, метрики/tracing.
- (direction) Success signal: SM-1 ≥99,9% событий доведены до DELIVERED при доступном подписчике за месяц; SM-2 ноль потерянных событий; SM-3 ноль дублей от повторов с тем же ключом; SM-5 медианная задержка публикация→первая отправка ≤ нескольких секунд.
- (assumption) Секрет подписки ≥16 символов (требует подтверждения); grace period 24ч конфигурируем; повторная ротация в переходе→409; конфликт тела при том же ключе→409; глобальное пространство ключей (следствие отсутствия мультитенантности).
- (assumption) Таймаут аренды 30с конфигурируем и строго больше таймаута отправки; 429 расходует номер попытки; двойная подпись списком в одном заголовке новая первой; макс 5 попыток; base/джиттер/потолок бэкоффа конфигурируемы (потолок не задан); множитель Retry-After-нет не задан; лимит хоста конфигурируется (дефолт не задан).
- (assumption) Publish/Subscriptions API без собственной аутентификации в v1 (защита периметром); сервис во внутренней сети; payload не логируется целиком; предполагается горизонтальное масштабирование.
- (question) Ожидаемая нагрузка: события/с, число подписок, размер payload — без этого нельзя задать пул воркеров, интервал опроса, лимит хоста.
- (question) Каков потолок Задержки повтора? (Retry-After может запросить больше, чем base×2^attempt).
- (question) Какова длительность grace period при ротации (принято 24ч как допущение)?
- (question) Значение лимита целевого хоста и переопределяется ли он на конкретный хост?
- (question) Значения таймаута аренды и периода реапера (принято 30с как допущение)?
- (question) Формат двойной подписи: список в одном заголовке через запятую или повторяющийся заголовок? — ломающее изменение для подписчиков, требует согласования.
- (question) Как долго хранятся События, Попытки и Ключи идемпотентности; нужна ли политика очистки?
- (question) Повторная публикация с тем же ключом, но другим телом: 409 Conflict или тихий возврат исходного События?
- (question) Как дежурный узнаёт о появлении dead letters при отсутствии алертинга в v1?
- (question) Планируется ли запуск более одного экземпляра? (влияет на локальность rate limiter).
