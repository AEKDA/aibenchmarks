# event-ingestion Specification

## Purpose

Описывает приём событий от внутренних систем через REST API с гарантией идемпотентности по заголовку `Idempotency-Key` и атомарным созданием события вместе с задачами доставки, чтобы ни одно принятое событие не потерялось и ни одна доставка не продублировалась.

## Requirements

### Requirement: Публикация события

Система SHALL принимать запрос `POST /api/v1/events` с телом JSON, содержащим `type` (тип события) и `payload` (произвольный JSON-объект), и при успехе возвращать `201 Created` с идентификатором сохранённого события.

#### Scenario: Успешная публикация

- **WHEN** отправлен `POST /api/v1/events` с заголовком `Idempotency-Key: key-1` и телом `{"type":"order.created","payload":{"order_id":42}}`
- **THEN** система отвечает `201 Created` и телом, содержащим `event_id`

#### Scenario: Пустой тип события

- **WHEN** отправлен `POST /api/v1/events` с корректным `Idempotency-Key` и пустым `type`
- **THEN** система отвечает `400 Bad Request` и событие не сохраняется

### Requirement: Обязательный заголовок Idempotency-Key

Система SHALL требовать непустой заголовок `Idempotency-Key` для каждого запроса `POST /api/v1/events` и отклонять запрос с `400 Bad Request`, если заголовок отсутствует или пуст.

#### Scenario: Заголовок отсутствует

- **WHEN** отправлен `POST /api/v1/events` без заголовка `Idempotency-Key`
- **THEN** система отвечает `400 Bad Request` и событие не сохраняется

#### Scenario: Заголовок пуст

- **WHEN** отправлен `POST /api/v1/events` с заголовком `Idempotency-Key: ` (пустое значение)
- **THEN** система отвечает `400 Bad Request` и событие не сохраняется

### Requirement: Идемпотентность приёма событий

Повторный запрос с уже использованным значением `Idempotency-Key` SHALL возвращать идентификатор ранее созданного события и NOT SHALL создавать ни нового события, ни дополнительных задач доставки.

#### Scenario: Повторный запрос с тем же ключом

- **WHEN** запрос с `Idempotency-Key: key-1` выполнен успешно, а затем отправлен ещё один запрос с тем же ключом
- **THEN** система отвечает успешным статусом с тем же `event_id`, что и в первый раз, и число доставок для этого события не увеличивается

#### Scenario: Конкурентные запросы с одним ключом

- **WHEN** два запроса с одинаковым `Idempotency-Key` обрабатываются одновременно
- **THEN** сохраняется ровно одно событие и ровно один набор доставок, а оба ответа содержат один и тот же `event_id`

#### Scenario: Разные ключи — разные события

- **WHEN** отправлены два запроса с одинаковым телом, но разными значениями `Idempotency-Key`
- **THEN** создаются два разных события, каждое со своим набором доставок

### Requirement: Атомарность события и его доставок

Система SHALL сохранять событие и порождённые им задачи доставки атомарно: при сбое на любом шаге сохранения не SHALL остаться ни события без доставок, ни доставок без события.

#### Scenario: Сбой хранилища при записи

- **WHEN** при сохранении события и его доставок происходит ошибка хранилища
- **THEN** система отвечает `500 Internal Server Error`, а в хранилище не остаётся ни частично записанного события, ни его доставок

#### Scenario: Доставки созданы в состоянии PENDING

- **WHEN** событие успешно опубликовано и ему соответствуют две активные подписки
- **THEN** создаются ровно две задачи доставки в статусе `PENDING`, каждая с нулевым числом выполненных попыток
